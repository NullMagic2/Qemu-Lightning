## Target

The overall goal is to develop a driver that implements **GPU paravirtualization and complete Windows GPU acceleration**, including the Windows desktop. Take every necessary implementation step to achieve this goal; a working installer, application-local translation layer or transport alone does not satisfy it. Keep the implementation small, follow style_guide.md, and use Rust 2024 for new Rust work; legacy Rust 2021 build paths still require migration.

1. Complete the Windows display path: VidPN negotiation and validation, supported modes, mode commit, primary allocation selection, source visibility and resolution changes. Reuse the existing BAR0 mapping and enforce BAR4 bounds and resource lifetimes. Keep display_ready disabled and RenderOnly=1 until the path works.
2. Implement native Direct3D runtime/UMD integration with truthful capabilities, device creation, resources/views, shaders, rendering operations and errors. Reuse suitable maintained components without treating application-local DXVK as a native WDDM UMD.
3. Complete WDDM allocation/residency, command scheduling, fences, shared resources and process isolation; implement DXGI/primary presentation, GDI interoperability and DWM composition.
4. Provide real presentation completion, refresh/vblank timing, pointer updates and safe interrupt-level behavior. The existing MMIO-flip capability cannot become an active display promise while its address path depends on a waiting Venus mutex or lacks a refresh clock.
5. Preserve correctness through cancellation, reset, timeout recovery, sleep/resume and PnP teardown. The current optional scanout is a CPU-copy XRGB8888 output, not a GPU flip engine: its BAR0 registers start at 0x300, and Rust validates pending geometry before copying BAR4 pixels into a QEMU-owned surface.
6. Deliver matching host/guest packages and normal-mode Windows installation through the applicable Microsoft signing process. A local development certificate does not satisfy that production requirement. Validate actual Windows loading, native D3D/DWM execution, resolution changes and frame pacing; count implementation progress separately from tests.
7. Provide AMD64 and WOW64 OpenGL through WGL -> Mesa Zink -> existing Venus ICD -> Lightning PCI -> isolated host Vulkan execution. Keep the exact Vulkan manifest and matching native loader beside the application. Build the separate C++ component with CMake at lightning/opengl; its optional QL_BUILD_MESA_OPENGL target requires an explicitly supplied pinned Mesa checkout, Meson and Ninja, and never downloads dependencies implicitly. QL_MESA_DEMOS_SOURCE_ROOT builds the unmodified upstream Mesa demos gears source as C++17. The source pin is ed458ffac6f410e6f03e54d17f47e8aeb55fe3a1; only Zink is built, with no software rasterizer. The opt-in QL_REACTOS_I386 build uses the exact supplied NT5 system DLL exports, kernel32_vista synchronization imports and C++ CRT adapters. Its dependency builds and import audits pass; native transport session and GPU-memory lifetime integration must pass in ReactOS before rendering is claimed. The checked C++ missing-DXGI factory fallback replaces an unavailable optional function pointer at the pinned loader boundary. Real ReactOS i386 vkCreateInstance now succeeds and loads the native Venus DLL; adapter enumeration awaits the missing LightningNT5 display-filter registration. This is startup evidence, not GPU rendering.

## QEMU overview

QEMU supplies the emulator, KVM integration, standard virtual hardware, VM management, display backends and build infrastructure. Its roughly 12,000 source files are upstream dependency code, not 12,000 files of our GPU implementation.
